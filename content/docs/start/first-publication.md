在本篇教程中，你将扮演一名空间数据维护人员，在 Web 控制台中创建项目和数据集，通过工作区保存一个监测点要素，将其发布为共享修订，随后修改该要素的属性，并通过“撤销（Restore）”功能安全地回退第二次修改。

完成本教程后，你将直观理解**工作区草稿（Draft）**、**共享修订**（Revision）与**反向撤销工作区**之间的区别。

## 前置条件

- 已按照 **[快速开始]({{< relref "/docs/start/quickstart/" >}})** 启动本地服务，并已在浏览器登录 `http://localhost:3000`。
- 当前登录账号具备创建项目的权限（初始管理员默认具备该权限）。

## 步骤 1：创建项目与数据集

首先，我们需要建立组织数据的容器：

1. 在控制台左侧导航栏进入 **项目** 页面，点击 **创建项目**，名称填写 `监测点演示`。
2. 进入新建的 `监测点演示` 项目，切换到 **数据集** 页面，点击 **创建数据集**（选择“创建模式”）。
3. 按以下参数填写数据集声明并提交：
   - **名称**：`stations`
   - **几何类型**：`Point`（点）
   - **坐标维度**：`2`（二维 XY）
   - **坐标系（CRS）**：`EPSG:4326`

> **概念提示**：数据集的几何类型、坐标维度与 CRS 在创建后即固定为该数据集的数据契约，后续写入的所有要素都必须符合这一声明。

## 步骤 2：新建工作区并保存要素草稿

在 GeoLedger 中，所有数据修改都先在**工作区**（Workspace）中进行，不会直接改动线上共享数据：

1. 在 `stations` 数据集页面点击 **浏览要素** 进入地图工作台。
2. 点击顶部工具栏的 **新建工作区**。此时界面会自动切换到新建的开放工作区（基础修订 `r0`，草稿编辑版本 `v0`）。
3. 点击 **添加要素**，将要素标识（ID）设为 `station-001`，在 GeoJSON 编辑框中填入以下完整 Feature，然后点击 **保存到工作区**：

```json
{
  "type": "Feature",
  "id": "station-001",
  "properties": {
    "name": "示例监测点",
    "status": "正常"
  },
  "geometry": {
    "type": "Point",
    "coordinates": [120.15, 30.27]
  }
}
```

保存成功后，你会观察到两个重要现象：
- **在当前工作区视图下**：地图和属性表中立即出现了 `station-001`，工作区编辑版本推进为 `v1`。
- **切换到“已发布的数据”视图时**：数据集仍然为空（项目 `HEAD` 仍为 `r0`）。这说明未发布的草稿对其他只读用户或线上查询完全隔离。

> **界面提示**：在 `v0.3.0-alpha.7` 中，保存后数据来源选择器中的版本号可能暂时停留在旧值；请以选择器旁的版本标记为准。

## 步骤 3：审阅差异并发布为修订 R1

确认草稿无误后，将其正式发布为项目级共享修订：

1. 进入左侧导航栏的 **工作区** 页面，点击当前工作区的 **变更**（Diff）。
2. 核对变更统计：`stations` 数据集包含 1 条新增要素（`station-001`），检查其属性与坐标。
3. 点击 **发布**，填写版本说明 `新增示例监测点`，确认提交。

发布成功后，系统会在同一数据库事务内更新正式数据表、记录版本历史并返回**发布回执（Receipt）**：
- 项目的共享修订推进为 **R1**（`r1`）。
- 原工作区状态转为 **已发布（published）**，不可再继续写入；后续新的编辑任务需创建新的工作区。

> **异常恢复提示**：如果在点击发布时恰逢网络闪断或超时，请勿重新创建工作区重复提交；控制台会在当前标签页保留原始发布请求 ID，你可以直接点击“重试原发布”安全确认结果（详见[发布结果恢复]({{< relref "/docs/guides/publication-recovery/" >}})）。

## 步骤 4：在新工作区中更新要素并发布 R2

现在我们模拟日常业务中的属性更新，并验证历史版本的时间旅行查询能力：

1. 返回 `stations` 数据集的地图工作台，点击 **新建工作区**（此时新工作区以 `r1` 为基础修订）。
2. 在地图或属性表中选中 `station-001`，点击 **编辑**，将其 `status` 属性从 `"正常"` 修改为 `"待复核"`（保持 `id`、`name` 与 `geometry` 不变），保存草稿：

```json
{
  "type": "Feature",
  "id": "station-001",
  "properties": {
    "name": "示例监测点",
    "status": "待复核"
  },
  "geometry": {
    "type": "Point",
    "coordinates": [120.15, 30.27]
  }
}
```

3. 前往 **工作区** 页面检查差异（此时显示 1 条修改，`status` 由 `"正常"` 变为 `"待复核"`），填写版本说明 `更新监测点状态为待复核` 并执行发布，生成修订 **R2**（`r2`）。

发布完成后：
- 查询当前最新共享数据（`HEAD = r2`）时，`station-001` 的 `status` 为 `"待复核"`。
- 当指定历史修订 `revision = 1` 查询时（或通过 API/SDK 读取 `r1`），`station-001` 的 `status` 依然准确返回当时的 `"正常"`。

## 步骤 5：非破坏性地撤销 R2 提交

假设我们发现 R2 的修改有误，希望将其回退。GeoLedger 不会抹去历史提交记录，而是通过生成**反向变更工作区**来完成撤销：

1. 进入左侧导航栏的 **版本历史** 页面，找到修订 `r2`（`更新监测点状态为待复核`）。
2. 点击该记录右侧的 **撤销（Restore）**，确认 **创建撤销工作区**。
3. 系统会自动创建一个新的开放工作区，并在其中写入能够抵消 `r2` 变更的草稿（即将 `station-001` 的 `status` 恢复为 `"正常"`）。
4. 在工作区页面审阅这份反向差异，填写版本说明 `回退 R2 的状态修改` 并点击 **发布**。

发布成功后，项目生成了新的修订 **R3**（`r3`）：
- 当前最新数据中，`station-001` 的 `status` 已恢复为 `"正常"`。
- 版本历史中完整保留了 `r1`、`r2` 和 `r3` 三次提交记录，审计链路清晰可查。
